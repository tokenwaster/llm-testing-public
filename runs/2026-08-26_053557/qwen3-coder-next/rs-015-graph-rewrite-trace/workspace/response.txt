We are given a sequence of 300 operations on a directed graph, starting from an empty graph. Operations include `ADD`, `DEL`, `MERGE`, `RENAME`, and `UNDO`. Our goal is to compute the **final state** of the graph after applying all operations in order, with `UNDO` cancelling the most recent *non-UNDO* operation (if any), and respecting ignore rules.

We need to output:
- `NUM_NODES`
- `NUM_EDGES`
- `REACHABLE`: number of nodes reachable from **EMBER** (excluding EMBER itself)
- `SHORTEST`: length of shortest directed path from EMBER to KARST, or `NONE`
- `MAX_OUT_NODE`, `MAX_OUT_DEGREE`: node with most outgoing edges; ties broken alphabetically
- `HAS_CYCLE`: YES/NO

### Strategy:

We need to simulate all operations **in order**, tracking:
- A set of nodes (strings)
- A mapping from each node → its outgoing neighbors (set of nodes, no duplicates)
- A stack of operations for `UNDO` (only non-ignored operations count toward UNDO)

But note: an ignored operation still counts as an operation that can be undone. So we must record every operation (including ignored ones) in the undo stack — but only non-UNDO ops go on the stack.

We also need to handle renames and merges carefully:
- When `RENAME x AS z` occurs, all outgoing/incoming edges of `x` now use name `z`. Future references to `x` refer to a new (possibly nonexistent) node.
- When `MERGE x INTO y`, all edges into/out of `x` are redirected to `y`, and `x` is removed.

Important: operations are processed **in order**, and `UNDO`s revert the effect of previous non-UNDO ops — but with ignore rules re-evaluated on replay (i.e., when replaying, we must not apply an operation that would have been ignored in the original context).

But wait! The problem says:

> "The final graph is the result of applying, in their original order, every operation that was never cancelled (with the ignore rules evaluated in that replay)."

That means: instead of undoing and reapplying, we need to simulate all operations *forward*, skipping those undone by an `UNDO`, but respecting ignore rules as if applied at that time.

But UNDOs are not commutative — operation order matters. So the only reliable way is:

- Maintain a stack of non-UNDO ops (with info whether they were ignored or not).
- On each `UNDO`, pop the most recent such op, and **remove** its effect — but only if it wasn’t ignored at the time.

But to correctly reverse effects:
- For `ADD a -> b`: just delete edge if exists.
- For `DEL a -> b`: re-add edge if it was deleted (i.e., we need to store whether edge existed before).
- For `MERGE x INTO y`: need to invert — restore `x`, move edges back. Complex: we’d need to record:
    - Before-merge edges of `x` (`out_x`, `in_x`)
    - Edges from/to `y` that may have duplicated
    - Nodes merged into `y`
    - Whether `y -> y` existed and got dropped.

Similarly, `RENAME x AS z`: need to rename back: map all `z` → `x`, free up `z`.

This is extremely complex to implement manually.
